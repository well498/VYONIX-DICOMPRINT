## 5. Regras para declarar APROVADO (evidência mínima)

1. Só com **execução real** no ambiente indicado na coluna `usuario`: instância do PC, proprietário ou local Linux.
   Teste local **nunca** aprova item de instância. CI só vale se o run id for citado.
2. A evidência precisa ter método + rota + status HTTP + trecho do corpo (ids e códigos de erro, sem senha, token,
   cookie ou CSRF) **ou** captura de tela com data/hora e usuário logado visível. Para testes de PC: comando e
   saída. Para os locais: comando e linha final do unittest (`Ran N tests ... OK`).
3. Teste negativo (403/409/422) só aprova se também ficar provado que **nada mudou**: GET posterior ou ausência do
   evento na auditoria.
4. Teste que muda dados: o evento correspondente precisa aparecer em `GET /admin/audit` (ação, ator, alvo), e o
   `audit/verify` final precisa dar `ok:true`.
5. Esperado "REQUISITO x Código" (UNI-04, UNI-05, PRM-02, RIS-11, TEL-09): se o comportamento do código se
   confirmar, o status é **REPROVADO** com o defeito citado. Não aprovar "porque o código faz isso".
6. Resultado diferente do esperado: REPROVADO + coluna `defeito` (ID, severidade, arquivo:linha suspeito). Sem
   ambiente, sem usuário ou com pré-requisito falho: BLOQUEADO + motivo.
7. T-ACE só fica APROVADO se todos os testes referenciados estiverem APROVADO. NI entra como lacuna declarada.
   Qualquer REPROVADO P0/P1 reprova o critério.
8. Sem dados reais em evidência: só nomes e identificadores DEMO.
