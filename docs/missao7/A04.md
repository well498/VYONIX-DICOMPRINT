## 1. Matriz de permissões da Central (itens 3–11, 15–17) — PROPOSTO

Regra geral: backend é a fonte; a UI só esconde (não substitui o 403). Cada item da linha/menu vem de `capabilities` calculadas
**por exame** no backend (ex.: `actions: ["view_images","open_report","share",...]`), para não duplicar regra no front.

| Elemento | Controle | Observação |
|---|---|---|
| Menu Início/Exames/Pacientes/Visualizador | `ris.exam.perform` ou `ris.exam.prepare` / `clinical.patients.read` / `pacs.studies.read` | Exames: **não** usar só `ris.schedule.read` (S7-04) |
| Configurações técnicas (visualizador alternativo) | `pacs.viewer.protocols` ou `core.settings.read` | ausente no papel técnico padrão |
| Colunas paciente/idade/sexo | `clinical.patients.read` + unidade | mostrar idade e sexo, não data de nascimento/CPF na lista (minimização) |
| Médico responsável / situação do laudo | `ris.exam.prepare` ou `report.read` | só nome e estado; nunca texto do laudo |
| Olho (Visualizar imagens) | `pacs.studies.read` + `viewing.can_see` + unidade | corrigir F-04 antes |
| Documento (Abrir laudo) | `report.read` **e** laudo liberado (signed) | técnico padrão não tem `report.read`: decisão do proprietário se o técnico lê laudo liberado; rascunho nunca |
| Compartilhar | nova `notify.patient.share` (ou `ris.exam.share` redefinida — hoje é compartilhamento interno; **não reutilizar** o mesmo código para dois significados) | e exame liberado |
| Atribuir médico / Prioridade | papel `tecnico` na unidade do exame + `lock` (não iniciado) | já no backend; exibir só se elegível |
| Comentários/pendências | `ris.exam.prepare` | já existentes (ExamComment/ExamFlag) |
| Achado crítico: registrar | `report.sign` (médico) | técnico: apenas "suspeita técnica"/encaminhar (ExamFlag), nunca classificar como achado diagnóstico |
| Desconsiderar / revisar | `ris.exam.cancel` com justificativa; revisão: supervisor | sem exclusão física |
| Painel de informações do paciente | `clinical.patients.read` + unidade do exame | auditar visualização? (recomendado: `patient.view` em painel com dados completos) |
| Lote | mesma checagem **por item** no backend; resultado individual | nunca "tudo ou nada" silencioso |

Multi-função: menu = união das permissões, sem duplicar telas (uma Central com filtros; ex.: médico+técnico vê uma só "Exames").
O técnico NÃO deve ver: Administração VYONIX, Usuários, Unidades, Configurações, Sistema, Auditoria, Minha produção/valores
(`report.production.*`), Comercial/Licença, Nós DICOM. Hoje o papel padrão já não tem essas permissões, exceto `core.license.read`
(confirmar que não gera menu).

## 2. Isolamento por unidade — correção mínima (PROPOSTO)

1. **Ingestão** (pacs/service.py:183): passar `site_id` do nó DICOM de origem (`node_for(calling AE, address)` → `DicomNode.site_id`).
2. **Conciliação** (clinical/service.py:reconcile): se `st.site_id is None` e o pedido tem `encounter_id`, herdar `Encounter.site_id`;
   se o estudo já tem unidade diferente da do atendimento → **Conflict** (não sobrescrever silenciosamente) e auditar `previous/new`.
3. **Endpoints da Central** (`exam-center`, `technician-panel`, novos): aplicar `c.p.sites_for(perm)` no SQL (não em Python após LIMIT).
4. **Estudo sem unidade**: deixar de ser "de todos". Visível/operável só por papel com escopo global (site_id NULL) e listado numa
   fila "Sem unidade" para conciliação. Exige mudar `exclusive.is_technician`, `_site`, `prep.queue` e `/clinical/studies`.
5. Backfill dos estudos existentes por script **reversível e auditado** (dry-run primeiro), aprovado pelo proprietário (A08).

Riscos: (a) instalações com papéis por unidade perderão acesso a estudos órfãos até o backfill (regressão do A07 V-03 — por isso item 4
deve vir junto com 1, 2 e 5); (b) nó DICOM compartilhado entre unidades ou sem `site_id` mantém órfãos; (c) AE title falsificável
na LAN — unidade derivada do nó é dado operacional, não prova de autorização; (d) mudança de unidade em estudo já laudado altera
quem o vê — bloquear após início do laudo.

## 3. Compartilhamento com o paciente (itens 11–13) — requisitos

Enquanto o Portal do Paciente não existir (404, módulo `patient` planejado): **o botão Compartilhar não deve gerar link funcional
nem enviar nada**. Opções seguras: ocultar, ou abrir a janela em modo "pré-visualização/simulação" (sem token válido, rotulado
"Portal do Paciente não disponível"), registrando o fluxo só em ambiente de teste. Não criar página pública provisória com laudo/PDF.

Requisitos (quando implementado):
- R1 Token: ≥128 bits aleatórios (`secrets.token_urlsafe(32)`), guardar **apenas hash** (SHA-256) no banco; nunca em log/auditoria.
- R2 Escopo: um token = um exame (study/report) de uma instituição e um paciente; não lista outros exames.
- R3 Liberação: só exame com laudo assinado/liberado e sem restrição (flag de bloqueio clínico/jurídico); revalidar no **acesso**, não só na emissão (laudo retificado/revogado invalida).
- R4 Expiração curta configurável (ex.: 7 dias), revogação manual e automática (mescla de pacientes, mudança de contato, cancelamento).
- R5 Autenticação antes do conteúdo: o link leva à tela do Portal; exige conta VYONIX ou desafio (data de nascimento + OTP no canal); limite de tentativas e bloqueio; nada clínico antes do sucesso.
- R6 Mensagem: sem nome do exame, modalidade, diagnóstico, médico ou anexo; apenas "Há um documento disponível na <instituição>" + link. Prévia exibida ao técnico = texto exato enviado.
- R7 Contato mascarado na UI e API (`(11) 9****-**21`, `jo***@d***.com`); valor completo nunca vai ao navegador do técnico.
- R8 Confirmação explícita no envio manual; destinatário = contato do **próprio paciente do exame** (não digitado livremente; alterar contato é ação de cadastro auditada).
- R9 Auditoria: quem, quando, canal, exame, destino mascarado, id do provedor, estado (fila/enviado/entregue/falhou), acessos ao link (IP, data, sucesso/falha de autenticação).
- R10 Idempotência: chave (exame, canal, contato, evento); reenvio dentro de janela exige ação explícita; fila persistente com tentativas limitadas.
- R11 Lote: cada item validado individualmente (liberado, paciente, instituição, consentimento); destinatário derivado do exame; resultado por item; nenhum token/mensagem agrega exames de pacientes diferentes.
- R12 Portal único: a identidade global só lê vínculos verificados; consulta da Clínica A nunca retorna dados da Clínica B (RLS por tenant no acesso do portal).
- R13 Sem envio real/serviço pago sem aprovação; provedor via "stub" em teste.

## 4. Consentimento / opt-out (LGPD)

Base legal: comunicação do resultado é execução de tutela da saúde/contrato (art. 11, II, f / art. 7º), mas canal (WhatsApp/e-mail)
deve respeitar preferência do titular. Requisitos:
- C1 Cadastro de contato com origem e data; preferência por canal (`whatsapp`, `email`) com estado `opt_in|opt_out|unknown`, registro de quem/quando/como.
- C2 Envio automático só com `opt_in`; manual com `unknown` exige confirmação de que o paciente autorizou (registrada); `opt_out` bloqueia no backend (não só na UI).
- C3 Opt-out fácil pelo próprio canal ("SAIR") e no Portal; efeito imediato; histórico preservado.
- C4 Dados ao provedor (WhatsApp Business/e-mail) = operador LGPD: contrato/DPA, só telefone/e-mail + texto neutro; registrar no RoPA.
- C5 Retenção: tokens expirados e logs de entrega com prazo definido; contato removível a pedido (com efeito na fila).
