## 1. Compartilhamento com paciente + histórico de envios

### 1a. `ris_0009_compartilhamento_paciente` (down=ris_0008; depends_on=report_0012)
Nome `patient_shares` para não confundir com `ris.exam_shares` existente.

`ris.patient_shares` (TenantMixin: id, tenant_id, created_at, updated_at, row_version)
- study_id FK clinical.studies NOT NULL; patient_id FK clinical.patients NOT NULL; site_id FK tenancy.sites NULL (cópia da unidade do estudo no momento)
- snapshot da liberação: report_id FK report.reports NOT NULL, report_version int NOT NULL, report_status varchar(10) NOT NULL (só `final` aceito pela aplicação), released_at timestamptz
- channel varchar(10) CHECK IN ('whatsapp','email','link'); origin varchar(8) CHECK IN ('manual','auto','lote'); batch_id uuid NULL
- recipient_masked varchar(80) (ex.: `(11) 9****-1234`, `m***@d***.com`); recipient_hmac char(64) (HMAC com chave fora do banco; deduplicação sem guardar o contato em claro)
- token_hash char(64) NOT NULL (SHA-256 do token; o token só existe no link enviado)
- created_by varchar(120), created_by_id uuid; expires_at timestamptz NOT NULL, CHECK (expires_at > created_at)
- revoked_at, revoked_by, revoked_by_id, revoke_reason varchar(300); last_access_at, access_count int server_default 0
- Estado (ativo/expirado/revogado) **derivado**, não armazenado.
Índices: `uq_ris_patient_shares_token (token_hash)` único global; `ix_ris_patient_shares_study (tenant_id, study_id, created_at)`; `ix_ris_patient_shares_patient (tenant_id, patient_id) WHERE revoked_at IS NULL`.
RLS: tenant_isolation padrão + FORCE. Privilégios: REVOKE ALL; app/service `SELECT, INSERT` + `UPDATE (revoked_at, revoked_by, revoked_by_id, revoke_reason, last_access_at, access_count, updated_at, row_version)` por coluna; sem DELETE.
Concorrência/duplicidade: `pg_advisory_xact_lock(hashtextextended('share:'||study_id||':'||channel||':'||recipient_hmac,0))` + reaproveitar link ativo em vez de criar outro (índice único não cobre expiração porque `now()` não é imutável).

`ris.patient_share_directory` (token_hash PK, tenant_id, share_id) **sem RLS**, padrão `auth.login_directory` (core_0002:31-32): app só `INSERT`; service `SELECT`. Necessário porque o portal resolve o token sem contexto de instituição; depois de achar o tenant, toda leitura volta a passar por RLS.
Quem escreve: serviço RIS (`share_with_patient`), portal (via service, só contadores de acesso). Auditoria: `ris.patient_share.create/revoke/access` (study_id, share_id, canal, destinatário mascarado — nunca token nem contato).
Validação no momento do INSERT (aplicação): laudo `final`, preparo ≠ `cancelled`, sem flag aberta `share_restricted` (novo código em `FLAGS`, sem migração — `exam_flags.code` é varchar(30)), paciente do estudo = paciente do pedido, tenant/unidade autorizados.
Dependência: Portal do Paciente **NÃO IMPLEMENTADO** (404) ⇒ link não tem destino; criar a tabela só junto com o endpoint de resolução.

### 1b. `notify_0001_fila_envios` (novo ramo `branch_labels=('notify',)`, depends_on=('core_0004','ris_0009'))
Alternativa, se não quiserem novo ramo: `ris_0010`. Recomendo `notify` porque o módulo já existe no manifesto (vyonix/modules/manifest.py:288) e será reutilizado por outros eventos.

`notify.deliveries` (TenantMixin)
- share_id FK ris.patient_shares NULL; study_id, patient_id NOT NULL (isolamento e "um paciente nunca recebe dado de outro": aplicação confere share.patient_id = delivery.patient_id)
- channel, recipient_masked, recipient_hmac; recipient_nonce/recipient_ciphertext bytea NULL (AES-GCM, chave própria `notify_contact_key`, mesmo padrão dos anexos ris; zerar para NULL ao chegar a estado final)
- template_code varchar(40), template_version int; idempotency_key varchar(120) NOT NULL
- provider varchar(20) server_default 'simulado'; provider_message_id varchar(120)
- status varchar(12) CHECK IN ('queued','sending','sent','delivered','read','failed','cancelled','blocked')
- attempts int default 0, max_attempts int default 5, next_attempt_at timestamptz, lease_until timestamptz, last_error varchar(300), sent_at, delivered_at, failed_at
- origin, batch_id, requested_by, requested_by_id
Índices: `uq_notify_deliveries_idem (tenant_id, idempotency_key)` único; `ix_notify_deliveries_due (next_attempt_at) WHERE status IN ('queued','failed') AND attempts < max_attempts`; `ix_notify_deliveries_study (tenant_id, study_id, created_at)`.
Chaves de idempotência: manual = UUID gerado pelo clique (reenvio do mesmo clique não duplica); lote = `lote:{batch_id}:{study_id}:{channel}`; automático = `auto:report_final:{report_id}:{version}:{channel}`.
Worker (papel service, `FOR UPDATE SKIP LOCKED` + lease). Privilégios: app `SELECT, INSERT`; service `SELECT, INSERT, UPDATE`; ninguém DELETE.
`notify.delivery_events` (delivery_id FK, status, detail varchar(300), at) — **somente INSERT** (REVOKE ALL; GRANT SELECT, INSERT), padrão report_starts.
Disparo automático: consumidor do `platform.outbox` existente (evento de laudo liberado) cria a entrega; configuração (manual/automático/canais/evento/modelo/remetente) em `platform.settings` módulo `notify` por unidade — **sem migração** (tabela já tem site_id e histórico).
Contato do paciente para modo automático: `clinical.patient_contacts` (patient_id, kind, value_ciphertext, value_hmac, masked, verified_at, consent_whatsapp_at, consent_email_at) em core_0006 **só se** o proprietário aprovar o automático (LGPD/consentimento). No manual, o técnico informa/confirma o destino e só fica mascarado + cifrado na entrega.

## 4. Unidade do estudo (F-02) — `core_0006_unidade_estudo_pedido` (down=core_0005)
Causa: `pacs/service.py:183-186` chama `clinical.register_study` sem `site_id`; pedido não tem unidade (só via `encounter_id`, sem rota para criar atendimento); `ris.schedules`/`ris.rooms` não têm unidade; `pacs.dicom_nodes.site_id` existe (pacs_0006:34, sem FK).
Colunas: `clinical.orders.site_id` uuid NULL FK tenancy.sites (unidade informada no pedido; DEMO "unidades variadas" não foram persistidas, A08-M4-02); `clinical.studies.site_source varchar(12)` CHECK IN ('pedido','atendimento','no_dicom','unica','manual') e `site_set_at`. Índices: `ix_studies_site_date (tenant_id, site_id, study_date)` e `ix_studies_sem_unidade (tenant_id) WHERE site_id IS NULL`.
Ordem de derivação no código (nunca sobrescreve unidade já definida): 1) pedido conciliado (`orders.site_id`, senão `encounters.site_id`) em `reconcile`; 2) nó DICOM pelo **AE chamador** (`actor 'dicom:<AE>'` → `dicom_nodes(tenant, ae_title)` único) na recepção; 3) instituição com uma única unidade ativa; 4) manual. **Não** usar `pacs.studies.source_ae` para estudos antigos de forma automática: ele prefere StationName (pacs/service.py:127-128,146), que pode coincidir com o AE de outra unidade ⇒ exposição entre unidades.
Migração dos existentes (incluindo DEMO): a migração só cria colunas. Atribuição em `tenancy.refresh` (padrão `ensure_main_admin`), idempotente, auditada `clinical.study.site` {from:null,to,source,how:'atualizacao'}, aplicando só fontes 1 e 3. O resto (provavelmente os 20 estudos DEMO: sem atendimento, 2+ unidades DEMO) fica NULL e vai para a lista "Estudos sem unidade" com prévia sugerida pelo nó (fonte 2), confirmada por administrador global; alterar unidade com `report_starts` existente exige justificativa. Depois: retirar `| Study.site_id.is_(None)` para papéis por unidade (ris/prep.py:515, routes_clinical.py:196) — A04/A03.
Precede: merge de `usuarios-admin-principal` (core_0005). Se 0.3.2 sair sem core_0005, **não** reutilizar o nome: core_0006 dependeria de uma revisão inexistente.
